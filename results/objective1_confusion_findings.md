# Objective 1 — confusion matrices, precision, recall and F1 at the operating threshold (2026-09-21)

Generated by `tools/detection_metrics.py`; every number below is in
`results/objective1_confusion/`. Same three fine-tuned detectors, same
678-image scene-split validation set as `objective1_accuracy_table.md`, run 2
weights (2026-09-11).

## Why this was run

mAP averages precision over every confidence threshold. The prototype runs at
one: `AssistController.confidenceThreshold = 0.30`, NMS IoU 0.45. A confusion
matrix at that threshold shows which errors a user would actually meet. A
pooled 0.170 does not.

## First: it is the same evaluation as the thesis already reports

Ultralytics' own `val()`, run locally on the same weights and split, reproduces
the Colab figures **exactly**: pooled mAP50-95 0.1254 / 0.1247 / 0.1696, and
every per-class AP50-95 and AP50 matches to four decimal places
(`crosscheck_vs_colab.csv`, max absolute difference 0.0000). So everything below
is computed on the evaluation Chapter 4 already reports, not on a lookalike.

## Protocol

- Predictions once per model at conf 0.001, NMS IoU 0.45 (the app's), one class
  per box (as the Core ML export's argmax gives). PyTorch weights, not the
  `.mlpackage`: the export matched the weights on a sample image but was not
  run across this set.
- Matching by Ultralytics' own `ConfusionMatrix.process_batch` (greedy by IoU,
  class-agnostic, one-to-one), at **confidence > 0.30** and **IoU > 0.5**.
- Each ground-truth object ends up in exactly one of three places: **correct**
  (matched, right class), **misclassified** (matched, wrong class) or **missed**
  (no box). Every box output ends up correct, misclassified or **spurious** (no
  object there).
- Precision = correct / boxes output. Recall = correct / objects.
  F1 = 2TP / (2TP + FP + FN). Micro sums over objects. Macro averages the 8
  classes present in validation, with a never-predicted class counted as 0.
- Detection has no true negatives, so "accuracy" is reported two ways, both
  read straight off the matrix. **Matrix accuracy** = correct / every non-empty
  cell. **Classification accuracy** = correct / objects that were matched at
  all, i.e. of the things it found, how many it named correctly.

## Headline — yolo26n at the operating threshold

| | count |
|---|---|
| objects in validation | 2,435 |
| found, right class | **502** |
| found, wrong class | 62 |
| missed entirely | **1,871** (77 %) |
| boxes on nothing (spurious) | 581 |

| metric | yolov8n | yolo11n | **yolo26n** |
|---|---|---|---|
| micro precision | 0.385 | 0.408 | **0.438** |
| micro recall | 0.163 | 0.172 | **0.206** |
| **micro F1** | 0.229 | 0.242 | **0.280** |
| macro F1 | 0.272 | 0.283 | **0.328** |
| weighted F1 | 0.220 | 0.228 | **0.271** |
| matrix accuracy | 0.133 | 0.142 | **0.166** |
| classification accuracy | 0.839 | 0.835 | **0.890** |
| recall ceiling (conf > 0.001) | 0.394 | 0.384 | **0.408** |

**The errors are misses, not confusions.** Of the 564 objects yolo26n puts a
box on, it names 502 correctly (89 %). What keeps F1 low is the 1,871 it never
boxes. The same holds for all three models (84–89 % classification accuracy
against 16–21 % recall). This narrows §5.2.2's open question. The weakness is
finding objects, not telling classes apart. It does not say *why* objects go
unfound.

**No threshold fixes it.** Even counting every box the model emits
(conf > 0.001), yolo26n finds only 41 % of objects with the right class. The
other 59 % are never correctly found at any threshold.

**0.30 is a well-placed threshold.** yolo26n's micro F1 peaks at 0.287 at 0.10
and is 0.280 at 0.30. Across 0.10–0.30 it moves by less than 0.01. Its macro F1
peaks exactly at 0.30 (0.328). Lowering the threshold would trade precision
(0.44 → 0.32) for a few points of recall (0.21 → 0.26), and F1 would not
change.

## Is the ranking real? Scene-level bootstrap

2,000 draws, resampling the 283 validation **scenes** with replacement, paired
across models (the same scenes every draw). Scenes rather than images, because
the three augmented copies of one photograph are not three independent
observations.

| micro F1 | point | 95 % CI |
|---|---|---|
| yolov8n | 0.229 | 0.191 – 0.270 |
| yolo11n | 0.242 | 0.200 – 0.286 |
| yolo26n | 0.280 | 0.237 – 0.327 |

| paired difference | micro F1 | macro F1 |
|---|---|---|
| yolo26n − yolov8n | **+0.051** (0.024 – 0.081) | **+0.056** (0.023 – 0.090) |
| yolo26n − yolo11n | **+0.039** (0.008 – 0.070) | **+0.046** (0.013 – 0.079) |
| yolo11n − yolov8n | +0.013 (−0.015 – 0.039) | +0.010 (−0.019 – 0.040) |

yolo26n's lead over both alternatives survives resampling on both averages.
Neither interval includes zero. yolov8n and yolo11n cannot be told apart. This
is the operating-point counterpart of the mAP ranking, and it agrees with it.

## Sensitivity: the 84 unaugmented images

Only 84 validation scenes are single images. Those are Roboflow's own
valid/test photographs, which carry none of its 3× augmentation. The other 196
scenes are each three augmented copies (vertical flip, 30° rotation), so part
of the full split is upside down.

| unaugmented (282 objects) | micro F1 | macro F1 |
|---|---|---|
| yolov8n | 0.247 | 0.297 |
| yolo11n | 0.279 | **0.341** |
| yolo26n | **0.288** | 0.292 |

yolo26n still leads on micro F1, but **yolo11n leads on macro F1**. With 282
objects every paired interval spans zero (yolo26n − yolo11n macro: −0.045,
−0.117 – 0.025). The clean subset is too small to confirm the ranking or to
overturn it. Report it as that, not as a reversal.

## Recall by object size (COCO pixel-area bands)

| | small (< 32²) | medium (< 96²) | large |
|---|---|---|---|
| objects | 544 (22 %) | 970 (40 %) | 921 (38 %) |
| yolov8n | 0.053 | 0.113 | 0.280 |
| yolo11n | 0.075 | 0.099 | 0.306 |
| **yolo26n** | 0.074 | 0.135 | **0.359** |

Recall rises steeply with size for every model. So small objects are a large
part of the misses, but not all of them: yolo26n still misses **64 % of large
objects**. Size explains the gradient, not the level.

`window` is the clearest size case. 686 of its 747 objects are small or medium,
and its recall is 0.14. `person` goes the other way, and it is the one anomaly:
large people are found *less* often (0.11, 139 objects) than medium ones (0.25).
Every other class that has both bands finds large objects more easily. That
points again at the source corpus's `person` annotations, as §5.2.2 already
suspects. It does not establish it.

| low_obstacle | 344 | 0.621 | 0.358 | 0.454 | 211 | 10 | 62 |
| stairs | 83 | 0.545 | 0.361 | 0.435 | 51 | 2 | 22 |
| table | 329 | 0.536 | 0.225 | 0.317 | 249 | 6 | 54 |
| door | 113 | 0.313 | 0.221 | 0.259 | 81 | 7 | 41 |
| window | 747 | 0.374 | 0.141 | 0.204 | 629 | 13 | 167 |
| person | 367 | 0.267 | 0.153 | 0.194 | 302 | 9 | 147 |
| chair | 368 | 0.392 | **0.103** | **0.163** | 321 | 9 | 56 |

The four untrained classes (`door_glass`, `pole`, `handrail`, `other`) have no
validation objects, and no model output a single box for any of them.

**The largest confusions are few, and they make sense.** window → door 10,
chair → table 9, person → low_obstacle 8, low_obstacle → person 6,
door → window 6, wall → door 4. Every one pairs classes that look alike or
overlap in the taxonomy. The largest share of any class is door → window, 6 of
113 doors (5 %).

**`stairs`, the highest hazard weight:** 30 of 83 found at 0.30 (recall 0.36),
and 55 % of stairs boxes are right. That is a per-photograph figure. Live use
sees a staircase across many frames, so a per-encounter rate would be higher
than 0.36. It would also be lowered again by Assist's 3-of-5 confirmation gate.
Neither effect was measured, so no per-encounter number is claimed.

## Caveats

- **"Spurious" is an upper bound on real false alarms.** A box with no labelled
  object under it may be a correct detection of something the annotators did
  not label. The corpus's annotation completeness has not been audited
  (§5.2.2), so precision here is a lower bound on true precision.
- PyTorch weights, not the Core ML export (see Protocol).
- One training run (run 2). Chapter 4 shows per-class AP moving substantially
  between runs, so per-class F1 from one run should be read as noisy as well.
- Validation images are photographs from the Roboflow corpus. §4.2.1 already
  shows the detector transfers poorly to the researcher's own captures, so
  these numbers are an in-distribution upper bound, not field performance.
